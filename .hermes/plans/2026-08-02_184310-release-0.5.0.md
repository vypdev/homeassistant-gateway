# Home Assistant Gateway 0.5.0 Implementation Plan

> **For Hermes:** Execute this plan incrementally with test-first slices, frequent commits, and full release gates. Do not publish 0.5.0 until every acceptance criterion below is verified.

**Goal:** Complete the Clean Architecture refactor, bounded asynchronous operations, frontend modularization, consumer documentation, runtime contract coverage, and release hardening required for a trustworthy `v0.5.0`.

**Architecture:** Keep the product as a Supervisor-managed Home Assistant App. Preserve the separation between Supervisor Ingress administration and direct authenticated MCP Streamable HTTP. Keep application use cases dependent on narrow read-only ports; keep FastAPI, MCP, HTTPX, SQLite, executor details, and Lit rendering at the outer boundaries.

**Tech Stack:** Python 3.11, FastAPI, Pydantic, SQLite, pytest, Ruff, TypeScript, Lit, Vite, Home Assistant Supervisor APIs, MCP Streamable HTTP, GitHub Actions, GHCR, Trivy.

## Release acceptance criteria

`0.5.0` is releasable only when:

1. All public existing HTTP/MCP contracts have compatibility tests.
2. All read-only application use cases depend on narrow protocols, not infrastructure classes.
3. Development jobs have bounded concurrency, retention, expiration, sanitized terminal errors, explicit shutdown, and tested race behavior.
4. No job can remain `running` indefinitely because of runner or persistence failures; timeout semantics are explicit and tested.
5. HTTP routes are separated into route modules with shared response/request models and middleware.
6. Home Assistant infrastructure is split into focused adapters without leaking credentials or arbitrary upstream bodies.
7. Frontend `main.ts` is reduced to shell/state composition; API, jobs, diagnostics, models, navigation and major views are separate modules.
8. Frontend has automated tests for polling, timeout, terminal states, empty results, retry and accessibility-sensitive rendering where practical.
9. Runtime i18n checks verify resolution in the active locale, not only key presence.
10. Consumer documentation describes installation, Ingress vs direct MCP, host allowlist, tokens, profiles, tools, errors, empty arrays and troubleshooting.
11. Local and remote release gates pass, including dependency audit, build, i18n, tests, CI, Release App, image manifest and Trivy.
12. Version metadata, changelog, release notes and image tag are all `0.5.0`.

## Definition of done

`0.5.0` is complete only when all phases A–H are either implemented or explicitly marked not applicable with a documented reason, all tests and gates are green, release workflows succeed, the multi-architecture image is verified, and the consumer documentation matches the deployed behavior.

No release should be published merely because the code compiles. The release requires contract evidence, runtime i18n evidence, frontend build evidence, security sanitization evidence and live MCP smoke-test evidence.
